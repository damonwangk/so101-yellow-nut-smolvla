# 03｜采集器怎样把演示变成可训练数据

[教程目录](../README.md) · [上一章](02-setup.md) · [下一章](04-timing.md)

> **学习目标：理解监督信号如何产生**
>
> 跟着一次相机新帧找到对应反馈、实际目标和时间。

最初先做试采，确认视频、关节和发送动作都能正确保存，再组织正式50条。试采与正式数据分别放在 `trial` / `formal`，各自独立编号，避免把调试片段混进正式训练。

```text
D:\so-101\datasets\yellow_nut_to_brown_tray\
  task.json
  trial\episodes\、sessions\、lerobot\
  formal\
    lerobot\       # 官方读取器直接读取的标准数据
    episodes\      # 逐条查看视图
    sessions\      # 控制、对齐和保存日志
    qc\            # 独立验收与预览，不改原数据
```

## 不是只录一个摄像头视频

`record-so101.py` 在同一个持续跟随会话中处理三条链路：控制循环读主臂、读从臂并发送受限目标；相机读取线程取得RGB图像及主机接收时间；写入线程接收对齐后的样本，写标准数据和逐帧日志。

每个观察到的新图像只保存一次，避免60Hz控制把30FPS画面重复保存两次。图像和时间戳在同一锁内读取，匹配**不晚于图像主机接收时间的最近一份从臂反馈**。同周期的动作使用原生驱动返回的实际发送目标，主臂输入另外保留用于诊断。

```python
# 示意：表达采集契约，完整实现见代码快照
image, image_received_at = read_camera_frame(camera)
sample = select_control_sample(control_history, image_received_at)
frame = {
    'observation.images.wrist_camera': image,
    'observation.state': sample['observation'],
    'action': sample['sent_action'],
    'task': TASK,
}
writer.submit(frame)
```

`state` 是当时测到的位置；`action` 是希望电机到达的位置，二者通常不完全相同。电机有响应时间，夹住物体后也可能无法到达空载闭合目标。不能把状态复制一份当动作，也不能在录完视频后凭画面猜出真实发送指令。

## 连续采集为什么保持跟随

正式入口 `开始黄色螺母正式采集50条.cmd` 调用批次脚本和 `record-so101.py --target-total 50`。本地Enter开始当前条；Q停止当前条录制并后台保存，**控制继续**；用主臂带从臂回到起点，重摆物体，等 `SAVED/READY` 后再次Enter。复位阶段不写进episode。

早期每条Q都会结束整个控制进程，释放力矩，从臂突然失去保持，第二次又必须重新连接和检查。最终把“录制状态”和“控制会话”分开：一次连接可录多条，退出整个批次才在托稳后按X释放。单条试采的Q仍是保存并退出，操作含义由入口决定。

## 保存与恢复的边界

有界写入队列向主线程传播写入错误；数值Parquet及时关闭；正常结束调用 `save_episode()` 与 `finalize()`，待视频编码及元信息落盘再标记提交成功。逐条目录、提交标记和 `batch-progress.json` 支持按已提交数量续接，重启不会从0覆盖已有条目。

连续多次Ctrl+C可能在编码或收尾过程中强行中断，因此正常结束要等 `SAVED`。曾在28条后暂停续采，最终采用已提交数量恢复和有限串口重试；若检测到残留力矩，必须由现场托稳后输入R才释放核验，不自动写新目标或重新校准。Windows MP4播放权限问题通过输出文件继承目标目录读取权限解决。


## 沿着一帧检查因果关系

用三个时间戳做一个教学例子：某张图主机接收时刻10.000s，已有从臂反馈9.990s和10.007s。当前匹配规则选9.990s，因为它是不晚于该图接收时间的最近反馈；不能为了“数值更近”选未来反馈。若图像来自相机内部更早的曝光，主机接收时间仍不能证明零延迟硬同步，所以另外保留时间日志供审计。示例时间为解释规则而设，实测间隔见数据验收报告。
